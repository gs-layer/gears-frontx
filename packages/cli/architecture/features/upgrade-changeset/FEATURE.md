## 1. Feature Context

- [x] `p2` - `cpt-frontx-feature-upgrade-changeset`

### 1.1 Overview

The Upgrade Change-Set Engine is the single `target` CLI-owned mechanism (`cpt-frontx-component-cli-change-set-engine`) that upgrades a registered template's **name** — every target that name has been applied to, as one unit of review and of record. `upgrade <templateName> <new-origin>` reads the name's current `{origin, version}` entry from `cpt-frontx-feature-composed-provenance`'s single project state document as its only baseline, resolves the new origin through the shared resolver, classifies every file inside every target listed under the name into a typed whole-file operation, presents the resulting operation plan for developer review, and — only on approval — commits the new `origin`/`version` (and the name's immediately preceding `{origin, version}`) in a single state-document write to the project state store, after landing the plan by per-file rename within each target's effective ownership. The recorded state cannot describe a partial upgrade — one target of a name at the new version while a sibling stays on the old one — because the registry records exactly one `origin` and one `version` per name; that bound is on the RECORD. The file writes before the single state-document commit are not one transaction across the tree: a failure the engine catches is recovered by an attempted rollback (reported with every path it could not restore when recovery itself fails), a failed commit-point state write leaves the landed files in place under an unchanged baseline record, and a hard crash runs no recovery at all; for the last two, both before the state-document commit, the intended remedy is the identical re-run, which converges under the preconditions the commit algorithm states and only as far as its bounded tests show (selected pre-commit points, inventory promotion and AI bundle refresh stubbed). No convergence is claimed for a crash after the commit: an identical re-run then finds nothing to upgrade, and an interrupted promotion or bundle refresh is not completed by it — whether to add such recovery is an open policy question, not decided here. All CDSL behavior is `target` (GREENFIELD — grounded in `cpt-frontx-adr-project-upgrade-mechanism`, `cpt-frontx-adr-project-provenance-record`, and DESIGN §3.2/§3.6).

The unit of operation is the template **name**, not one applied instance, and the baseline is the single registry entry that name carries: the registry records one `origin`/`version` pair per name, covering every target that name has been applied to. There is no per-instance provenance record to diff against, and none is retained for the purpose. The feature's identifier, `cpt-frontx-feature-upgrade-changeset`, covers the per-target, per-file change set of typed whole-file operations — `ADD`, `REPLACE`, `REMOVE`, `KEEP_LOCAL`, `UNCHANGED` — computed once for the whole name by a three-way classification against the baseline the registry entry re-resolves, carried as data in the CLI's single JSON result envelope, applied through a staged write that never rewrites a file the developer has changed, and reversed by the same engine one generation back. A doubly-changed file — one the candidate and the on-disk content have each moved away from the baseline — is refused whole, with `CONTENT_CONFLICT`, never merged or partially rewritten.

### 1.2 Purpose

This feature exists to let a project developer safely adopt a newer origin for any registered template, across every target it has been applied to, without hand-editing files or risking an unreviewed change, or one whose failure goes unreported: a failure the engine catches before the commit-point state write triggers an attempted rollback and names every path it could not restore, a state-write failure after the files landed is reported while the files stay landed, and a hard crash or a concurrent process is outside any rollback, per the commit algorithm; for a failure before the state-document commit the intended remedy is convergence on re-run under the preconditions it states, and nothing is claimed for a crash after that commit. It satisfies `cpt-frontx-fr-cli-project-upgrade-changeset` (the upgrade is one change set covering all of a name's targets, whose recorded `origin`/`version` moves in a single project-state document replacement; the file writes before it are not one transaction across the tree — the bounded guarantee is stated in the commit algorithm), `cpt-frontx-fr-cli-upgrade-review-approval` (no file is written until the developer approves), and `cpt-frontx-fr-cli-upgrade-restore` (an approved upgrade remains reversible). The engine is reusable across invokers — direct CLI use and AI-driven orchestration (`cpt-frontx-feature-ai-upgrade-orchestration`) both drive the same engine, never a second implementation.

`cpt-frontx-adr-project-upgrade-mechanism` fixes the unit of upgrade (a template name, planned and reviewed as one unit across all its targets, with a single state-document commit), the source of its baseline (the project state store's `origin`/`version` entry, forward and preceding alike), the changeset representation, the three-way whole-file classification that computes it, the staged write and failure recovery that apply it, and the one-generation reversal that undoes it. This feature's validation and commit algorithms carry out that mechanism directly: validation classifies every file inside the candidate's effective ownership against the baseline and the candidate and refuses the whole upgrade with `CONTENT_CONFLICT` on any doubly-changed file, or with `TARGET_CONFLICT` where the candidate newly claims ground another registered target nests inside, including a sibling target recorded under the same name; commit lands the classified plan through a staged write and, on success, records the one preceding `{origin, version}` the reversal needs. `cpt-frontx-fr-cli-upgrade-restore`'s reversibility requirement is carried out by the identical engine run in the other direction (see §5, "Restore to Pre-Upgrade State").

### Developer Review and Approval of an All-Targets Upgrade

- [x] `p1` - **ID**: `cpt-frontx-flow-upgrade-changeset-review-approval`

**Actor**: `cpt-frontx-actor-project-developer`

**Realizes**: `cpt-frontx-cli-seq-upgrade-review-apply`

**Success Scenarios**:
- Developer approves the validated operation plan; the engine commits the new `origin`/`version` and the name's immediately preceding `{origin, version}` in a single state-document write for the name (not one transaction with the file writes, which land first by per-file rename), and lands every `ADD`/`REPLACE`/`REMOVE` operation within each target's candidate-manifest-bounded effective ownership, writing nothing to a `KEEP_LOCAL` or `UNCHANGED` path and nothing to a path reported `SKIPPED`.

**Error Scenarios**:
- The name has no entry in the project state store: `TEMPLATE_NOT_REGISTERED`.
- The name's `targets` array is empty: the engine refuses with `TARGET_NOT_APPLIED`, directing the developer to `register --replace` instead — there is no applied ground for `upgrade` to reconcile.
- The name's recorded `version` no longer matches what its recorded `origin` reports: the engine refuses with `VERSION_MISMATCH` before resolving the candidate origin, because the baseline it would diff against is not the state the project actually holds.
- The new origin cannot be resolved: `ORIGIN_UNAVAILABLE`; the engine reports the failure and aborts before writing anything.
- The new origin's manifest declares a `name` different from the registered name being upgraded: the engine refuses with `REGISTRATION_CONFLICT`, naming both identities, and computes no transition — a registered name's identity comes from exactly one place, its own manifest, and `upgrade` must not silently re-key an entry to a different template.
- A file inside any target's candidate-bounded effective ownership has both moved away from the baseline and does not already match the candidate: the engine refuses the entire upgrade with `CONTENT_CONFLICT`, naming every such target and path, and `templates[name]` is left unchanged for every target.
- Ground the candidate newly claims because it dropped an exclusion the baseline manifest declared nests another registered target: the engine refuses the entire upgrade with `TARGET_CONFLICT`, naming the contesting target and registered name, and `templates[name]` is left unchanged for every target.
- After approval, the commit algorithm can still refuse or fail: a pre-rename drift refusal (`CONTENT_CONFLICT`, no destination touched), a recovered I/O failure (`INTERNAL`, every target exactly as before), a failed recovery (`INTERNAL` naming both the original failure and every path it could not return, though one or more destinations may not be at their baseline state), a promotion failure after the commit point (`INTERNAL` naming the slot, with `templates[name].origin`/`.version` and its preceding pair standing committed regardless), or an AI-extension bundle refresh failure after promotion (`INTERNAL` naming the bundle, with the transition and the promoted inventory entry both standing). The engine reports these two post-commit failures as `INTERNAL`; the `frontx upgrade` command, which records the transition (project receipt and `templates[name].pendingPostCommit`, written in the commit write itself), answers them as `RECOVERY_REQUIRED` with that code as `details.cause` and `transitionCommitted: true`, and every writer of the project refuses until `frontx upgrade <name> --recover` finishes the remaining task after a fresh review.
- The name's entry still carries an unfinished post-commit record (`pendingPostCommit`) from an earlier transition: the engine refuses with `RECOVERY_REQUIRED` before computing any plan or no-op; nothing written.
- The confirming `--json --yes` call carries no `--plan-digest`, or one that does not match the recomputed plan (AI bundle review included): nothing is applied and the answer is `CONFIRMATION_REQUIRED` carrying the current plan and its digest.
- Developer declines the presented operation plan: no project files are written and `templates[name]` and the local inventory entry are left unchanged.
- Another registered name with an applied target has an AI-bundle directory that nests with or equals the upgraded name's: the engine refuses with `REGISTRATION_CONFLICT`, `details: { name, overlapping }`, before resolving the new origin; nothing written.

### Developer Restores a Template's Pre-Upgrade State

- [x] `p1` - **ID**: `cpt-frontx-flow-upgrade-changeset-restore`

**Actor**: `cpt-frontx-actor-project-developer`

**Use cases**: `cpt-frontx-usecase-upgrade-applied-template` (postcondition)

**Success Scenarios**:
- Developer requests restore via `frontx upgrade <templateName> --restore`; the engine runs the same classification, review, and staged write in the other direction — the name's recorded preceding pair as the candidate, the currently recorded entry as the baseline, the boundary computed from the preceding manifest — reverses `templates[name].origin`/`.version` and every target's applied content, within that boundary, back to the preceding state as one recorded transition across every target of the name (the file writes carry the same bounded guarantee as a forward upgrade, not a cross-tree transaction), and records the origin it just left as the new preceding origin. A file the forward upgrade added into ground the current manifest had newly claimed lies outside the preceding manifest's boundary and stays exactly where it is, reported `SKIPPED` rather than reverted.

**Error Scenarios**:
- `templateName` has no entry in the project state store: the engine refuses with `TEMPLATE_NOT_REGISTERED`.
- `templateName`'s `targets[]` is empty: the engine refuses with `TARGET_NOT_APPLIED`, exactly as the forward direction does — there is no zero-target reversal that flips `origin`/`version` with no content moved.
- No `{origin, version}` is recorded as the name's preceding entry — the name has never been upgraded, or a later `register --replace` cleared the pair a prior upgrade or restore had recorded: the engine refuses with `NOTHING_TO_RESTORE`.
- The validation this flow invokes refuses: `VERSION_MISMATCH` when the currently recorded entry's own honesty check fails (the same check a forward upgrade's baseline gets) or when the recorded preceding origin resolves but reports a version different from the one recorded beside it; `ORIGIN_UNAVAILABLE` when the recorded preceding origin cannot be resolved at all; `REGISTRATION_CONFLICT` when the recorded preceding origin's manifest declares an identity different from `templateName`.
- A file inside any target's preceding-bounded effective ownership has both moved away from the current baseline and does not already match the preceding pair's content: the engine refuses the entire restore with `CONTENT_CONFLICT`, naming every such target and path, and `templates[name]` is left unchanged for every target.
- Ground the preceding manifest no longer excludes nests another registered target: the engine refuses the entire restore with `TARGET_CONFLICT`, naming the contesting target and registered name.
- After approval, the commit algorithm can still refuse or fail, exactly as a forward upgrade's can: a pre-rename drift refusal (`CONTENT_CONFLICT`, no destination touched), a recovered I/O failure (`INTERNAL`, every target exactly as before), a failed recovery (`INTERNAL` naming both the original failure and every path it could not return, though one or more destinations may not be at their baseline state), a promotion failure after the commit point (`INTERNAL` naming the slot, with `templates[name].origin`/`.version` and its new preceding pair standing committed regardless), or an AI-extension bundle refresh failure after promotion (`INTERNAL` naming the bundle, with the transition and the promoted inventory entry both standing). The engine reports these two post-commit failures as `INTERNAL`; the `frontx upgrade` command, which records the transition (project receipt and `templates[name].pendingPostCommit`, written in the commit write itself), answers them as `RECOVERY_REQUIRED` with that code as `details.cause` and `transitionCommitted: true`, and every writer of the project refuses until `frontx upgrade <name> --recover` finishes the remaining task after a fresh review.
- Developer declines the presented operation plan: no project files are written and `templates[name]` is left unchanged.
- Another registered name with an applied target has an AI-bundle directory that nests with or equals the restored name's: the engine refuses with `REGISTRATION_CONFLICT`, `details: { name, overlapping }`, before the preceding pair is consulted; nothing written.

         1. [x] - `p1` - **RETURN** `INTERNAL` naming the original failure; every target and `templates[templateName]` are exactly as they were before the attempt - `inst-rst-return-commit-recovered`
      4. [x] - `p1` - **IF** the commit reports a failed recovery - `inst-rst-if-commit-recovery-failed`
         1. [x] - `p1` - **RETURN** `INTERNAL` naming both the original failure and every path recovery could not return; `templates[templateName]` remains untouched, though one or more destination paths may not be at their baseline state - `inst-rst-return-commit-recovery-failed`
      5. [x] - `p1` - **IF** the commit reports a promotion failure - `inst-rst-if-commit-promotion-failed`
         1. [x] - `p1` - **RETURN** `INTERNAL` naming the slot it could not replace; `templates[templateName].origin`/`.version` and its new preceding pair stand committed — the transition itself lands, only the inventory entry's promotion did not; the command surfaces this as `RECOVERY_REQUIRED` with the inventory task still pending - `inst-rst-return-commit-promotion-failed`
      6. [x] - `p1` - **IF** the commit reports an AI-extension bundle refresh failure - `inst-rst-if-commit-bundle-refresh-failed`
         1. [x] - `p1` - **RETURN** `INTERNAL` naming the bundle it could not refresh; `templates[templateName].origin`/`.version`, its new preceding pair, and the promoted inventory entry all stand committed — only the bundle refresh did not land; the command surfaces this as `RECOVERY_REQUIRED` with the AI task still pending - `inst-rst-return-commit-bundle-refresh-failed`
      7. [x] - `p1` - **RETURN** success: the name and every one of its targets are at the preceding state within the preceding manifest's boundary, and the name's preceding entry now names the origin restore just left - `inst-rst-return-success`
   6. [x] - `p1` - **ELSE** (developer declines) - `inst-rst-else-declined`
      1. [x] - `p1` - Engine makes no changes to any project file, to `templates[templateName]`, or to the local inventory entry - `inst-rst-no-write-on-decline`
      2. [x] - `p1` - **RETURN** declined - `inst-rst-return-declined`

## 3. Processes / Business Logic (CDSL)

### Validate a New Origin Against Every Target of a Name

- [x] `p2` - **ID**: `cpt-frontx-algo-upgrade-changeset-validate`

**Input**: The registered name's current baseline `{origin, version, targets[]}`; a candidate `new-origin`; optionally, for a restore invocation only, the recorded expected version beside the candidate origin, checked against what the resolved candidate reports (a forward upgrade's candidate carries no such recorded expectation and never supplies this).

**Output**: A validated operation plan `{ from: {origin, version}, to: {origin, version}, targets[], operations[], skipped[] }` — `operations[]` a per-target, per-file list of `{ target, path, op }` where `op` is one of `ADD`, `REPLACE`, `REMOVE`, `KEEP_LOCAL`, `UNCHANGED`, and `skipped[]` a per-target, per-path list of payload paths left untouched because they fall outside the candidate-bounded effective ownership or because they collide with the reserved temporary-file naming convention — ready for review; or an idempotent no-op when the candidate resolves to the baseline's own `{origin, version}`; or a failure naming why validation did not pass (`VERSION_MISMATCH` for a baseline the project state misreports, or for a candidate carrying a recorded expected version that no longer matches what it resolves to, `ORIGIN_UNAVAILABLE` for an unresolvable origin, `REGISTRATION_CONFLICT` for a declared-identity mismatch, `INVALID_PATH` naming every target and location that is not spelled as the one project location it names, or every target and path where the leaf itself, or an ancestor, is a symlink whose resolved target escapes the project root, `CONTENT_CONFLICT` naming every target and path where a file has both moved away from the baseline and does not already match the candidate — separately naming, within that report, which of those paths are instead uncomparable because of an unreadable disk shape rather than genuine content drift — or `TARGET_CONFLICT` naming every target and template where the candidate newly claims ground another registered target nests inside).

**Steps**:
1. [x] - `p1` - Confirm the recorded baseline is still honest before anything is computed from it, and obtain the baseline payload and the baseline manifest's declared `excludedSubtrees` classification will compare against: resolve the name's currently recorded `origin` and compare the version it reports against the `version` recorded beside it in the project state document - `inst-val-check-baseline`
2. [x] - `p1` - **IF** the recorded `version` differs from the version the recorded origin now reports - `inst-val-if-baseline-drift`
   1. [x] - `p1` - **RETURN** `VERSION_MISMATCH` naming the template name, its recorded version, and the version its recorded origin now reports; no transition is computed and no target is inspected, because a transition computed from a baseline the project state misreports would diff against a version this project never actually had. For a pinned remote origin this can only mean `.frontx/project.json` was hand-edited or corrupted, since an immutable pin re-fetches identically (`cpt-frontx-adr-source-spec-syntax`); for a `path:` origin it is genuine drift in the local folder, which has no publication to pin against — the same two cases `cpt-frontx-feature-composed-provenance`'s `validate --project` distinguishes for this code - `inst-val-return-baseline-drift`
3. [x] - `p1` - Resolve `new-origin` through the shared resolver (`cpt-frontx-feature-template-resolution`), pinning it exactly as `register` would; this resolution pins the candidate and makes its content addressable without replacing the registered name's own entry in the local template inventory, which keeps holding the baseline's content throughout — this is the only resolution of `new-origin` this algorithm performs, and a caller (including restore) never re-resolves it beforehand - `inst-val-resolve-new-origin`
4. [x] - `p1` - **IF** resolution fails - `inst-val-if-resolve-fail`
   1. [x] - `p1` - **RETURN** `ORIGIN_UNAVAILABLE` - `inst-val-return-unavailable`
5. [x] - `p1` - **IF** a recorded expected version was supplied for the candidate and the resolved candidate now reports a different version - `inst-val-if-candidate-version-mismatch`
   1. [x] - `p1` - **RETURN** `VERSION_MISMATCH` naming the name, the recorded expected version, and the version now reported; no target is inspected — the same baseline-honesty semantics this algorithm already applies to the baseline, applied here to a candidate that itself carries a recorded expectation, which is what a restore's preceding pair is - `inst-val-return-candidate-version-mismatch`
6. [x] - `p1` - Read the resolved manifest's declared `name` and its declared `excludedSubtrees` - `inst-val-read-name`
7. [x] - `p1` - **IF** the resolved `name` differs from the registered name being upgraded - `inst-val-if-identity-mismatch`
   1. [x] - `p1` - **RETURN** `REGISTRATION_CONFLICT` naming both identities; no target is inspected - `inst-val-return-identity-mismatch`
8. [x] - `p1` - **IF** the resolved candidate's `{origin, version}` equals the baseline's currently recorded `{origin, version}` - `inst-val-if-candidate-is-baseline`
   1. [x] - `p1` - **RETURN** an idempotent no-op: no operation plan is computed, no destination is written, and the name's preceding pair is left exactly as it is. The project state DOCUMENT may still be written, and exactly once — when the entry carries no recorded `excludedSubtrees` (`inst-if-noop-missing-exclusions` above), the outcome names what it recorded, because a no-op for the `{origin, version}` pair is not a no-op for a document missing a field this engine writes — an upgrade to where the name already is does not consume the one generation of reversal - `inst-val-return-noop`
9. [x] - `p1` - **IF** another registered target (including a sibling target under the same name) has since become a symlink, after its directory was moved elsewhere and its former path was replaced with a symbolic link to it — its files then live at the RESOLVED location, which classification, comparing the spelling of each path, would judge as this name's own ground — judge that resolved location as well - `inst-val-judge-resolved-other-targets`
   1. [x] - `p1` - **RETURN** `TARGET_CONFLICT` naming every target of this name that coincides with, or sits inside, such a resolved location, before any target is classified; a resolved location strictly inside one of this name's targets is reserved exactly as another template's origin folder is, never written to, only where the baseline's declared `excludedSubtrees`, the candidate's, and what this name recorded when it was applied (a recorded value marked `exclusionsBackfilled` counts as none) all carve that ground out of the target — undeclared, it is this name's own payload and is refused with the same `TARGET_CONFLICT` rather than quietly skipped - `inst-val-return-resolved-other-conflict`
10. [x] - `p1` - **FOR EACH** target in `targets[]` - `inst-val-foreach-target`
   1. [x] - `p1` - Invoke the classification algorithm (`cpt-frontx-algo-upgrade-changeset-classify`) for that target against the baseline payload, the baseline manifest's `excludedSubtrees`, the candidate payload, and the candidate manifest's `excludedSubtrees`; accumulate the target's returned per-file operations and `skipped` paths, or, for a doubly-changed file or a nested-target conflict, the target and every path or contesting target it names, together with the classification's own marking of which doubly-changed paths are uncomparable and which of those escape the project root - `inst-val-check-target`
   2. [x] - `p1` - Collect, before the first target is classified, the ground EVERY registered template (this one included) recorded as `relinquishedGround`, each root as spelled and as resolved, so an alias of that ground is covered as well - `inst-val-protect-retained-ground`
   3. [x] - `p1` - **IF** an operation the classification returned for a target is a `REMOVE` or a `REPLACE` whose path lies inside that ground (spelled or resolved; a path that cannot be resolved inside the project counts as inside), drop it from the operations and report the path `SKIPPED` with the reason `RETAINED_GROUND` instead. The classification compares bytes only, so an old file that happens to equal the baseline copy of this payload reads as this template's own; `cpt-frontx-feature-cli-scaffolding`'s deletion plan preserves the same ground, and the upgrade must not destroy what delete keeps (human ruling V2, preserved across successive upgrades). Only these two operations are held back: an `ADD`, an `UNCHANGED`, a `KEEP_LOCAL` and a refusal inside that ground behave as everywhere else, the entry's `relinquishedGround` is carried unchanged; the reviewable plan gains an optional `retainedGround` list of `{template, ground}` naming EVERY recorded ground that held a skipped path (`RetainedGroundHolder`; several entries may overlap, and the list is not a per-path mapping), leaving each skip exactly `{target, path, reason}`; the notes tell the person the ground stays protected while any holder remains and that removing a holder does not by itself say the held files may be removed. Which regions are retained is decided as follows: a marked entry's `provenExcludedSubtrees` evidence (kept narrowed, see `cpt-frontx-feature-composed-provenance`) covers regions excluded in every write it made, so a repeated upgrade with unchanged exclusions does not retain them again, while a region it handed over or took back, and any entry without evidence, stays retained. The cost is deliberate conservatism: a template whose target lies inside retained ground (a guest in a host's relinquished subtree) does not have its files there rewritten or removed by an upgrade, and the plan names each one. What the developer or an agent sees is fixed, not incidental: the skip is a `{target, path, reason}` record in the plan, the upgrade succeeds, and the recorded `{origin, version}` advances to the candidate in the same run although those files were not brought to it, so a repeat of the upgrade is a no-op and a later upgrade compares against the advanced version (what the next upgrade does with a held-back file follows the classification, not a fixed result: equal to the next version is `UNCHANGED`; equal to the recorded version while the next one differs is a `REPLACE` when the next payload carries different content for the path, or a `REMOVE` when the next payload omits it, and either, inside relinquished ground, is held back again as `RETAINED_GROUND`; differing from the recorded version and from the next version is a `CONTENT_CONFLICT` only when the recorded and next payload bytes also differ from each other, and `KEEP_LOCAL` when they are equal, in which case the file is left as it is and nothing is reported as skipped). The plan presented before approval words this as a condition (if approved the files will be left as they are and the version will advance; declining writes nothing); the line printed after the commit is past tense. No output advises overwriting or removing the files. `upgrade --restore` is an ordinary upgrade to the previous origin, not a state-only rewind: its plan can `REPLACE`, `REMOVE` or `ADD` current files, refuse, or skip paths outside the restored boundary (`OUTSIDE_BOUNDARY`), and is reviewed like any other - `inst-val-skip-retained-ground`
11. [x] - `p1` - **IF** any target named a location classification did not judge because it is not spelled as the one project location it names (`inst-cls-judge-spelling`) - `inst-val-if-unaddressable`
    1. [x] - `p1` - **RETURN** `INVALID_PATH` naming every such target and location and why it was not judged; every target is classified before this check runs, so no partial pass is ever returned, and nothing was read from disk for any of those locations or written anywhere. Checked first of all the conflict classes below: a location that was never read, compared or planned leaves a hole in the plan every later check would otherwise be judging - `inst-val-return-unaddressable`
12. [x] - `p1` - **IF** any target named a doubly-changed path recorded because the leaf itself, or an ancestor, is a symlink whose resolved target escapes the project root - `inst-val-if-escaping-ancestor`
    1. [x] - `p1` - **RETURN** `INVALID_PATH` naming every such target and path; every target is classified before this check runs, so no partial pass is ever returned. Checked, and refused, before the content-conflict check below: whether a path is even addressable inside the project at all is the more fundamental question, the same ordering `cpt-frontx-algo-cli-scaffolding-uniform-apply`'s own pre-flight containment check already settled for the identical on-disk shape on the apply side - `inst-val-return-escaping-ancestor`
13. [x] - `p1` - **IF** any target named a doubly-changed path - `inst-val-if-target-fails`
    1. [x] - `p1` - **RETURN** `CONTENT_CONFLICT` naming every such target and path, and separately naming which of those are uncomparable because the disk shape cannot be compared at all (a directory or a symlink at the leaf, or a symlink or a regular file at an ancestor directory component) rather than because content genuinely drifted — the two causes name different remedies, so the report distinguishes them rather than collapsing them into a single disjunction; every target is classified before this check runs, so no partial pass is ever returned - `inst-val-return-target-fail`
14. [x] - `p1` - **IF** any target named another recorded target nested inside newly claimed ground (including a sibling target under the same name) - `inst-val-if-nested-conflict`
    1. [x] - `p1` - **RETURN** `TARGET_CONFLICT` naming every such target and the contesting registered name; every target is classified before this check runs, so no partial pass is ever returned - `inst-val-return-nested-conflict`
15. [x] - `p1` - **RETURN** the validated operation plan `{ from: {origin, version}, to: {origin: <resolved>, version: <resolved>}, targets[], operations[], skipped[] }`, `operations[]` and `skipped[]` carrying every target's accumulated results - `inst-val-return-pass`

### Classify a Target's Files Against Baseline and Candidate

- [x] `p2` - **ID**: `cpt-frontx-algo-upgrade-changeset-classify`

**Input**: One target; the currently recorded origin (baseline) and its manifest's declared `excludedSubtrees`; the requested new origin (candidate) and its manifest's declared `excludedSubtrees`; `projectOwnedRoots`, `.frontx`, the reserved environment entries, and the template's own local origin folder (when installed by local path); every target already recorded across every registered template's `targets[]` in the project state store; the baseline payload and the candidate payload (each resolved).

**Output**: The target's per-file operations — a list of `{ target, path, op }` where `op` is one of `ADD`, `REPLACE`, `REMOVE`, `KEEP_LOCAL`, `UNCHANGED` — together with every payload path reported `SKIPPED` because it falls outside the candidate-bounded effective ownership or because it collides with the reserved temporary-file naming convention; or, for a doubly-changed file or another recorded target nested inside newly claimed ground (including a sibling target under the same name), the target and every such path or contesting target, for the caller to refuse the whole upgrade with `CONTENT_CONFLICT` or `TARGET_CONFLICT`; or, for the target or a payload path that is not spelled as the one project location it names, that location and why, for the caller to refuse the whole upgrade with `INVALID_PATH`. Every doubly-changed path is additionally reported as uncomparable — the disk shape at (or above) it cannot be compared at all, rather than the candidate and the disk each genuinely having moved away from the baseline — when that is why it was recorded, together with the specific component responsible (the leaf itself, or the offending ancestor) and its kind, and, within that, as escaping the project root when the specific cause is a symlink — at the leaf itself, or at an ancestor — whose resolved target does; the caller uses those two distinctions to refuse `INVALID_PATH` for an escaping symlink ahead of `CONTENT_CONFLICT` for everything else, and to name each remaining path's own cause and remedy in the `CONTENT_CONFLICT` report.

**Steps**:
1. [x] - `p1` - Judge the target, and every path either payload declares re-rooted under it, on its NORMALISED project-relative spelling before anything else is computed from it. The target is a string recorded in the project state store, which a developer or a pull request can edit; a payload path reaches this algorithm by roads the resolver's own bundle-key check (`inst-resolve-bundle-keys`, `cpt-frontx-feature-template-resolution`) does not cover — a local `path:` origin's file listing among them — and this algorithm's own containment must hold with that check removed. A location is judged only when it is already spelled as the one location it names: not absolute, not climbing out of the project root, and carrying no `.`, `..` or empty segment and no trailing separator. Every ownership comparison below is made segment by segment on the string it is handed, so `app/../other/x.txt` would read as ground inside `app` while landing in `other`, and `app/../.frontx` as a target that `.frontx` does not exclude. A location that is not so spelled is not enumerated, not compared, not read from disk, not probed through its ancestors and not planned; it is recorded, with why, for the caller to refuse the whole upgrade with `INVALID_PATH`, and an unjudgeable target ends this algorithm for that target at once. This is the rule `cpt-frontx-algo-cli-scaffolding-uniform-apply` already rests on — a target is canonicalized before it is used and a payload path is the path of a real directory entry, neither of which can carry a `..` segment — stated here for the two inputs this algorithm receives only as strings. The project state store's own load (`inst-psio-if-noncanonical`, `cpt-frontx-algo-composed-provenance-project-state-io`) already refuses a recorded target or `projectOwnedRoots` entry spelled any other way (or carrying a control character or surrounding whitespace), for every engine, and this engine's own load refuses a `projectOwnedRoots` entry that reaches its ground through a symlink (`inst-psio-if-aliased-owned-root`); the judgement here is the engine's own defence for a caller that hands it strings the store did not load, and for payload paths, which the store never sees. A payload path that lands on the target itself rather than inside it is not addressable either, and one unaddressable path refuses the payload as a whole: nothing is compared, boundary-checked or read for its siblings - `inst-cls-judge-spelling`
2. [x] - `p1` - Compute the target's effective ownership boundary once, from the candidate manifest's declared `excludedSubtrees` together with `projectOwnedRoots`, `.frontx`, the reserved environment entries, and the template's own local origin folder — the same six-term subtraction `cpt-frontx-algo-cli-scaffolding-uniform-apply` performs (`inst-ua-compute-ownership`) — and subtract, on top of it, every OTHER registered template's local origin folder, exactly as the apply path does in its own separate step (`inst-ua-subtract-other-origins`). That term is named here rather than left implied in the citation: without it an upgrade could classify a path inside a sibling template's own source folder as `ADD`/`REPLACE`/`REMOVE` and write through it, which is the hazard that step was added to `apply` to prevent — never the baseline manifest's `excludedSubtrees`, and never recomputed per path - `inst-cls-compute-candidate-boundary`
3. [x] - `p1` - Compute the target's effective ownership boundary the same way from the baseline manifest's declared `excludedSubtrees` — the boundary the target's content was actually written through at its last apply or upgrade - `inst-cls-compute-baseline-boundary`
4. [x] - `p1` - **FOR EACH** path, in the baseline payload or the candidate payload, that falls outside the candidate boundary computed above — whether because the candidate manifest's `excludedSubtrees` now excludes ground the baseline owned, or because `projectOwnedRoots`, `.frontx`, a reserved environment entry, or the template's own local origin folder excludes it regardless of what changed between the two manifests, including ground a nested other template's target already legitimately occupies (always inside a declared `excludedSubtrees` entry, per `cpt-frontx-algo-cli-scaffolding-conflict-check`'s own containment rule) — leave its on-disk content exactly as it is, make no comparison for it, and record it `SKIPPED` - `inst-cls-skip-excluded`
5. [x] - `p1` - **FOR** the ground that falls inside the candidate boundary but was outside the baseline boundary — ground the candidate no longer excludes, newly claimed and ordinary eligible ground — resubmit it against every other recorded target, including this name's sibling targets, through the nesting-aware check (`cpt-frontx-algo-cli-scaffolding-conflict-check`) - `inst-cls-if-newly-claimed-nested`
   1. [x] - `p1` - **IF** another registered target nests inside that ground, record the target and its registered name as a nested-target conflict for this target; the rest of that ground remains ordinary eligible ground for classification below - `inst-cls-record-nested-conflict`

      The comparison includes every recorded sibling target under the same name, using the already-resolved baseline exclusions for those targets; only the target currently being classified is omitted from its own comparison. If a candidate drops or narrows an exclusion so newly claimed ground contains one of those siblings, validation refuses with `TARGET_CONFLICT` before presenting a plan. Keeping the exclusion preserves the supported nested-target arrangement.
6. [x] - `p1` - Enumerate every path appearing in the baseline payload or the candidate payload, confined to the candidate boundary computed above, excluding any path already reported `SKIPPED` — never every path the boundary merely admits, so a developer's own file, symlink, or directory sitting inside the boundary at a path neither payload ever declared is not enumerated, not compared, and never reaches the plan at all (`cpt-frontx-adr-project-upgrade-mechanism`: "a developer's own file or symlink sitting there that neither payload ever declared is not examined at all"). That exclusion is what keeps the plan reviewable: such a path would classify `KEEP_LOCAL` and write nothing, but it would still occupy a line in the plan a developer reviews and approves, and a target at the project root would bury the handful of real operations under one no-op line per file in the repository. A path matching the reserved temporary-file naming convention the commit algorithm's write phase uses (`inst-com-materialize-temp`) is excluded from comparison the same way — never compared — but not silently: it is instead recorded `SKIPPED`, naming the reserved-convention collision as the reason, exactly like a path the boundary itself excludes. That reporting is reached by a path a PAYLOAD declares; a stale temporary file merely sitting on disk is reclaimed by the commit algorithm's own first step (`inst-com-reclaim-stale-temp`), never by classification. A directory or a symlink where a payload DOES declare that exact path is still enumerated and refused fail-closed by `inst-cls-if-not-regular` below. For a published template, a payload path matching the reserved convention is refused outright before publication by the content self-containment validation `cpt-frontx-feature-template-manifest` owns (`inst-csc-if-reserved-name`, `cpt-frontx-algo-template-manifest-validate-content-self-containment`); a local `path:` origin has no publication step for that check to run against, so this `SKIPPED` reporting is the only guard such a payload ever meets - `inst-cls-enumerate`
7. [x] - `p1` - **FOR EACH** enumerated path - `inst-cls-foreach-path`
   1. [x] - `p1` - Read the path's content, or its absence, from the baseline payload, the candidate payload, and on disk; comparison is defined over absence explicitly — an absent path is unequal to any content, and two absences are equal - `inst-cls-read-three`
   2. [x] - `p1` - **IF** this path is carried by the baseline payload or the candidate payload, and the disk holds a directory, a symlink, or a special file (a FIFO, socket, or device — anything that is neither a regular file, a directory, nor a symlink) at this exact path instead of a regular file or an absence, **OR** any directory component of the path from the project root down to the leaf's parent — `target`'s own component included, never only the components strictly below it — is itself reported as a symlink, as an ordinary regular file, or as a special file where a directory is required — the same extension `cpt-frontx-algo-cli-scaffolding-existing-content`'s own `inst-ec-if-symlink-component` already makes on the apply side for the symlink and special-file cases, applied here in this algorithm's own terms rather than imported, because that helper probes one full-tree walk while this algorithm probes one injected `readDiskEntry(absolutePath)` call per path: a symlinked ANCESTOR is invisible to a leaf-only `lstat`, since the OS transparently resolves every intermediate path segment on both a read and a write, so without this clause a symlinked ancestor directory would let this step compare — and the commit algorithm land — content at wherever the link actually points, never at the path the plan names. `target`'s own component is covered by this probe because `target` is a string recorded in the project state store, never canonicalized by this algorithm the way `apply`'s pre-flight canonicalizes a batch's own target before reconciliation ever runs — so a `target` that is itself a symlink, or that sits beneath one, would otherwise reach this classification unresolved. A regular file standing where a directory is required is refused identically: the leaf cannot be reached on disk the way the payload declares it either way. A SPECIAL FILE standing at an ancestor position is a DIFFERENT hazard from a symlinked one, not a variant of it: the OS does not resolve it elsewhere the way it does a symlink, it simply refuses to descend past it, so every path beneath it reads back as an ABSENCE rather than as content at some other location — left unflagged, that absence would satisfy this same algorithm's own "two absences are equal" rule and report nothing to do for content this step never actually managed to read, which is a false success, not a misdirected comparison - `inst-cls-if-not-regular`
      1. [x] - `p1` - Record the path as doubly-changed for this target, fail-closed, for any of these causes; no comparison is attempted, and a special file's own content is never read to reach this conclusion — opening a FIFO for reading can block forever waiting for a writer that will never arrive. When the cause is a symlink — at the leaf itself, or at an ancestor — whose resolved target escapes the project root, this is additionally distinguished from every other cause in this step, for the caller to refuse the whole upgrade with `INVALID_PATH` rather than `CONTENT_CONFLICT` — the same code `cpt-frontx-algo-cli-scaffolding-uniform-apply`'s own pre-flight containment check already reports for the identical on-disk shape on the apply side, naming "this path cannot be proven to stay inside the project" as a more fundamental problem than "a symlink stands here, resolve it" - `inst-cls-record-not-regular`
   3. [x] - `p1` - **ELSE IF** the disk content already equals the candidate's content for this path — tested first, before every other branch below, including when both are absent, because there is nothing to do for a path already at its intended state regardless of what the baseline holds - `inst-cls-if-unchanged`
      1. [x] - `p1` - Classify the path `UNCHANGED` - `inst-cls-return-unchanged`
   4. [x] - `p1` - **ELSE IF** the path is present in the candidate, absent from the baseline, and absent on disk - `inst-cls-if-add`
      1. [x] - `p1` - Classify the path `ADD` - `inst-cls-return-add`
   5. [x] - `p1` - **ELSE IF** the path is present in the candidate, the candidate differs from the baseline, and the disk content equals the baseline — a REPLACE writes the candidate's content, so candidate presence is required; a candidate that omits a path the baseline carries is never a REPLACE and falls to the REMOVE step below - `inst-cls-if-replace`
      1. [x] - `p1` - Classify the path `REPLACE` - `inst-cls-return-replace`
   6. [x] - `p1` - **ELSE IF** the path is present in the baseline, absent from the candidate, and the disk content equals the baseline - `inst-cls-if-remove`
      1. [x] - `p1` - Classify the path `REMOVE` - `inst-cls-return-remove`
   7. [x] - `p1` - **ELSE IF** the candidate equals the baseline and the disk content differs from the baseline — including a path both versions carry identically that the developer has deleted, where the deletion is itself the edit - `inst-cls-if-keep-local`
      1. [x] - `p1` - Classify the path `KEEP_LOCAL`; the developer's own edit stands and no write is ever planned for this path - `inst-cls-return-keep-local`
   8. [x] - `p1` - **ELSE** (the candidate differs from the baseline and the disk content differs from both the baseline and the candidate — including a candidate that adds a path the disk already carries content for that the baseline does not account for, and a path the developer deleted that the candidate also changes) - `inst-cls-else-conflict`
      1. [x] - `p1` - Record the path as doubly-changed for this target; it is not classified as an operation - `inst-cls-record-conflict`
8. [x] - `p1` - **IF** any path was recorded as doubly-changed, or a nested-target conflict was recorded, for this target - `inst-cls-if-any-conflict`
   1. [x] - `p1` - **RETURN** the target and every doubly-changed path and every nested-target conflict it names, marking within the doubly-changed paths which are uncomparable (an unreadable disk shape rather than genuine content drift) and, within those, which escape the project root through an ancestor symlink, for the caller to refuse the whole upgrade with `INVALID_PATH` for an escaping path ahead of `CONTENT_CONFLICT` for every other doubly-changed path, or with `TARGET_CONFLICT` for a nested-target conflict; no file is written, merged, or partially rewritten - `inst-cls-return-conflict`
9. [x] - `p1` - **RETURN** the target's per-file operations list together with its `SKIPPED` paths - `inst-cls-return-ops`

### Commit the All-Targets Transition

- [x] `p2` - **ID**: `cpt-frontx-algo-upgrade-changeset-commit`

**Input**: An approved operation plan (name, `targets[]`, `from {origin, version}`, `to {origin, version}`, `operations[]`).

**Output**: Every `ADD`/`REPLACE`/`REMOVE` operation landed within its target's effective ownership; `templates[name].origin`/`.version` committed to `to` together with the name's immediately preceding `{origin, version}`, as the transition's one commit point; the registered name's local inventory entry then promoted by re-resolving the committed remote origin (when the name is installed from one); the name's CLI-owned AI-extension bundle then refreshed. Or: when a destination's own reserved temporary path is already occupied by anything other than a regular file — a shape this algorithm never puts there itself — `CONTENT_CONFLICT` naming every such destination, with nothing yet materialised or touched anywhere. Or: when the pre-write verification finds a destination has drifted from what classification saw, `CONTENT_CONFLICT` naming every drifted destination, with no destination touched. Or: when an I/O failure anywhere inside the TRY is caught and recovery succeeds, every target, the project state store, and the inventory entry left exactly as they were before the attempt, `INTERNAL` naming the original failure. Or: when that recovery itself fails, `INTERNAL` naming both the original failure and every path recovery could not return. Or: when promotion fails after the commit point, `INTERNAL` naming the slot it could not replace, with the transition itself standing. Or: when the AI-extension bundle refresh fails after promotion, `INTERNAL` naming the bundle it could not refresh, with the transition and the promoted inventory entry both standing.

**Steps**:
1. [x] - `p1` - **TRY**: - `inst-com-try`
   1. [x] - `p1` - Before materialising any new temporary file, remove any stale REGULAR FILE matching the reserved naming convention below already inside any target's effective ownership — left behind by a prior attempt on this name that crashed before landing it; a regular file is the only shape this algorithm's own convention ever produces at such a path, so it alone is reclaimed with any confidence it is this algorithm's own past litter - `inst-com-reclaim-stale-temp`
   2. [x] - `p1` - For every `ADD`/`REPLACE` operation, before materialising anything, inspect what already stands at its own reserved temporary path - `inst-com-verify-temp-occupancy`

      1. [x] - `p1` - **RETURN** `CONTENT_CONFLICT` naming every such destination TOGETHER WITH its own reserved temporary path — the destination is the ground the developer approved, but the reserved temporary path is where the offending shape actually stands, and a refusal naming only the former leaves the developer with nothing to find anything wrong at; nothing has been materialised or touched at this point, for this destination or any other — refused, never reclaimed and never written through: a live symlink standing here would otherwise have new content written through it to wherever it actually points, and the rename that follows would then move the link itself, not a regular file, into the destination - `inst-com-return-temp-occupied`
   4. [x] - `p1` - For every `ADD` and `REPLACE` operation across every target, materialise its new content into a temporary file beside its destination path, named by appending a reserved suffix this engine alone uses to the destination's own filename — a convention classification excludes from every comparison (`inst-cls-enumerate`), so a crash cannot leave litter that later classifies as a developer's own file — mutating no destination path in this step.    5. [x] - `p1` - **IF** that exclusive-create write itself fails because something now occupies this operation's own reserved temporary path — a race in the window step 4's own backstop exists to close - `inst-com-if-temp-occupied-at-write`
      1. [x] - `p1` - **RETURN** `CONTENT_CONFLICT` in the identical shape `inst-com-return-temp-occupied` already returns, naming this one destination and its reserved temporary path; nothing has been renamed yet, so there is nothing to restore to baseline, only this attempt's own temporary files already materialised for an earlier operation in this same step, which are removed before returning - `inst-com-return-temp-occupied-at-write`
   6. [x] - `p1` - Once every temporary file for every target of the name exists, and immediately before the first rename, verify that every destination the plan touches still holds exactly the content classification saw for it (or, for a `REMOVE`, still equals the baseline content classification saw) - `inst-com-verify-destinations`
   7. [x] - `p1` - **IF** any destination no longer matches what classification saw - `inst-com-if-drift-detected`
      1. [x] - `p1` - **RETURN** `CONTENT_CONFLICT` naming every drifted destination; no destination has been touched at this point, so there is nothing to recover — this is a precondition check, never a recomputation, and it can only refuse, never change what was approved. [x] - `p1` - Once verification passes, land each `ADD`/`REPLACE` operation by an atomic rename of its temporary file over its destination — creating any parent directory the rename needs — and unlink each `REMOVE` operation's path without removing the directory it leaves empty, confined throughout to each target's effective ownership and never to a nested target belonging to another registered target, including a sibling target under the same name; a `KEEP_LOCAL` or `UNCHANGED` path is never opened for writing - `inst-com-apply-within-boundary`

[x] - `p1` - Return each destination path already landed at the point of failure to its baseline state: write baseline content where the baseline payload carries the path (a landed `REPLACE`), and unlink where the baseline payload does not carry it (a landed `ADD` is reversed by unlinking, never by writing content the baseline does not have); re-resolve the baseline payload rather than reading it from any retained snapshot; ALSO remove every temporary file this attempt materialised whose operation never reached the rename phase — never a destination, so there is no baseline content to restore for it, only its own existence, created by this attempt, to undo; write nothing to the project state document and nothing to the inventory entry. A failure caught before the first rename — during reclaim, materialisation, or verification — has landed no destination yet, so this step has nothing to return, and, when no `ADD`/`REPLACE` operation had yet been materialised either, nothing to remove — vacuously, trivially successful either way - `inst-com-restore-on-error`
   2. [x] - `p1` - **IF** every returned destination path lands back at its baseline state AND every such temporary file is removed - `inst-com-if-recovery-succeeds`

   3. [x] - `p1` - **ELSE** (recovery itself fails for one or more destination paths or temporary files) - `inst-com-else-recovery-fails`
      1. [x] - `p1` - **RETURN** `INTERNAL` naming both the original failure and every destination path or temporary file recovery could not return or remove; `templates[name]` and the inventory entry remain untouched, though one or more destination paths may not be at their baseline state and one or more temporary files may remain on disk - `inst-com-return-recovery-failure`
3. [x] - `p1` - As the single atomic write that is this transition's commit point, write to the project state store: commit `templates[name].origin`, `.version`, and `.excludedSubtrees` to `to`'s (the CANDIDATE payload's) values, together with the name's immediately preceding `{origin, version}` — the `from` this transition started at. `excludedSubtrees` is recorded from the candidate, never the baseline: an upgrade can narrow or widen what a name excludes, and `cpt-frontx-feature-cli-scaffolding`'s deletion-plan algorithm trusts this recorded value over re-resolving the origin. This is the only atomic write in this algorithm; once it lands, the transition has committed regardless of what the next step does. When the command records the transition, this same write carries the entry's `pendingPostCommit` — the transition's id and its post-commit tasks (`inventory`, `ai`: `pending`, `done` with a verified effect hash, or `not-required`) — which only verified finalization clears (`cpt-frontx-feature-composed-provenance`). 4. [x] - `p1` - **IF** that commit-point write itself fails - `inst-com-if-commit-state-fails`
   1. [x] - `p1` - **RETURN** `INTERNAL` naming the store failure (the store makes a best-effort attempt to remove its own temp file, and a cleanup failure never replaces the original error, which is the one reported; a failed cleanup can leave that temp on disk, where it is never read as state; what remains may be partial, since a failed temp write can stop part-way, and is a complete copy of the candidate document only when the temp write had finished before the failure, as in a rename failure); every destination write has already landed, so — unlike every other `INTERNAL` this algorithm returns — this is NOT a recovered-to-baseline outcome and nothing is rolled back: the recorded entry still names the baseline, which is what lets re-running the identical upgrade converge rather than refuse (`inst-cls-if-unchanged`'s disk-equals-candidate precedence) when the same baseline and candidate still resolve and nothing else touched the project in between — the convergence the algorithm's hard-crash paragraph and the staged-write requirement state as MUST under exactly those preconditions, and which holds for no other state because no cross-process lock backs it. Rolling the landed destinations back here would be the strictly worse answer: it would undo work the developer approved in order to recover a document that was never written - `inst-com-return-commit-state-failure`
5. [x] - `p1` - As a separate write to a separate store, never described as part of the write above, promote the committed origin into the registered name's own entry in the local template inventory — for an installed remote origin, through the bounded update fed with the candidate bytes this command already acquired for review (no second fetch), after which the slot and its index entry are read back and must hold exactly the approved candidate before the task counts as done; a local `path:` origin or a name never installed has no slot and nothing to promote - `inst-com-replace-inventory`
6. [x] - `p1` - **IF** that promotion fails - `inst-com-if-promotion-fails`
   1. [x] - `p1` - **RETURN** `INTERNAL` naming the slot it could not replace; the transition itself stands — `templates[name].origin`/`.version` and the preceding pair recorded in step 3 remain committed, and the inventory task stays pending in `pendingPostCommit` for `--recover` - `inst-com-return-promotion-failure`
7. [x] - `p1` - The engine refreshes `name`'s CLI-owned AI-extension bundle at `.frontx/ai/<manifest-name>/` to exactly the AI snapshot the developer reviewed as part of the plan (`plan.ai`: the candidate payload's own `.frontx/ai/<manifest-name>/` bytes against the destination as it then stood) — writing only those bytes, removing what only the destination held, and only while the destination is still exactly what was reviewed (`cpt-frontx-algo-cli-scaffolding-ai-bundle`, `cpt-frontx-feature-cli-scaffolding`) - `inst-com-refresh-bundle`
8. [x] - `p1` - **IF** that refresh fails - `inst-com-if-bundle-refresh-fails`
   1. [x] - `p1` - **RETURN** `INTERNAL` naming the bundle it could not refresh; the transition and the promoted inventory entry both stand, defined the same way a promotion failure is, and the AI task stays pending in `pendingPostCommit` for `--recover` - `inst-com-return-bundle-refresh-failure`
9. [x] - `p1` - **RETURN** success: the operation plan applied and `templates[name]` updated for every target - `inst-com-return-success`
   1. [x] - `p1` - Include, alongside the applied plan, every reserved-suffix path step 1 reclaimed for this attempt — a developer's own prior crashed run left real litter on disk, and reporting it here is what lets them see it was cleared rather than never learn it existed - `inst-com-report-reclaimed-temp`

A hard crash — one this algorithm's own `CATCH` never observes — runs no recovery. A crash before the commit point (step 3) leaves the recorded entry still naming the baseline, so re-running the identical upgrade **MUST** converge on the intended state by the disk-equals-candidate precedence rule (`inst-cls-if-unchanged`) rather than refusing, under the stated preconditions (the same baseline and candidate still resolve, and nothing else — no concurrent process, no outside edit of the project, the registered origin or the state document — intervened; there is no cross-process lock) — and the project state document it then writes, protection fields (`exclusionsBackfilled`, `relinquishedGround`, `provenExcludedSubtrees`, `excludedSubtrees`) included, **MUST** equal what an uninterrupted run would have written, because the commit derives them from the unchanged baseline entry and the plan alone, never from partially landed disk state a skipped or retained path could not have changed: every path the crashed run had already landed already equals the candidate and needs no further write, every path it had not yet reached is landed normally, and any stale reserved-suffix temporary file the crash left behind inside a target's effective ownership is reclaimed by that re-run's own first step (the project state store's own atomic-write temporary file, `.project.json.<uuid>.tmp`, is not that kind of file. After a CAUGHT store failure — a failed temp write or a failed rename — the store makes a best-effort attempt to remove exactly its own temp (never another process's file) and reports the original error whether or not that removal succeeds; if the removal itself fails, the temp stays on disk as residue, partial or complete depending on whether its write had finished, treated like the orphan below. After a SIGKILL between its write and its rename no catch runs, so the temp stays orphaned: it is never read as state, is not reclaimed by a re-run, survives a converged retry, and is left to the developer to delete. Convergence is therefore judged on the authoritative state document and the managed destinations, not on the whole repository tree). A crash after the commit point but before promotion or the bundle refresh completes leaves the transition committed and that later step incomplete; nothing depends on either being immediately current, since any later resolution of the name's now-recorded origin re-derives the same content. That convergence, together with the repository's own version control for anything the preconditions exclude, is the whole remedy, and this algorithm makes no all-or-nothing claim across the project tree after a hard crash, after a recovery that could not restore every path, after a commit-point state-write failure, or while another process operates on it; the simulated-crash test `src/__tests__/upgrade-crash-convergence.test.ts` (in-memory disk, throwing seams) and `src/__tests__/upgrade-crash-convergence-real-fs.test.ts` (real filesystem, real adapters and state store, a SIGKILLed child process after each rename, at each unlink and between the state store's temp write and rename, two targets, counted writes to already-landed paths, a real directory as exclusion evidence) pin the convergence requirement for a crash between renames, a partial REMOVE set, a crash before and during the state write, and a caught state-write failure, including a real store rename failure after its temp was written (which must leave no own temp behind when the removal succeeds and, when the removal itself also fails, must still report the original error with the store's own temp, complete because its write had finished, as the only residue; a failure during the temp write itself can leave a partial temp and is not pinned by that test) — not power-loss durability, which atomic rename alone does not establish; no rollback journal is retained for it, because the baseline payload the recovery above depends on is re-resolvable rather than stored.

### Guard a Transition Through the Shared Mutation Boundary

- [x] `p2` - **ID**: `cpt-frontx-algo-upgrade-changeset-mutation-boundary`

**Input**: A writing command (an upgrade or restore among them) for one project root, in `normal` mode, or in `recover` mode for `upgrade <name> --recover`; the inventory root the local inventory was built with.

**Output**: The command runs inside the boundary and, for an upgrade or restore, its one transition is recorded before any effect and released only from a verified terminal state; or the command is refused before its first read-to-write check (`RESOURCE_BUSY`, `RECOVERY_REQUIRED`). This boundary serializes cooperating same-user writers only; it is not a cross-process lock against any other writer and adds no all-or-nothing guarantee to the commit algorithm.

**Steps**:
1. [x] - `p1` - Acquire the per-user namespace mutex for the whole command, before its first read-to-write check - `inst-mb-acquire`
2. [x] - `p1` - **IF** another writer holds the mutex past the wait bound - `inst-mb-if-busy`
   1. [x] - `p1` - **RETURN** `RESOURCE_BUSY`; nothing read or written - `inst-mb-return-busy`
3. [x] - `p1` - Collect every blocking record: an unknown entry in the inventory root's coordination directory, any malformed or unknown record, any reservation of this physical inventory root (in `recover` mode, except one belonging to this project), any transition receipt of this project (in `recover` mode these are handed to the recovery algorithm instead; a receipt recorded for another project root is refused outright), and any reservation of this project without its receipt; in `recover` mode only, this boundary's own interrupted temporary record files are removed - `inst-mb-collect-records`
4. [x] - `p1` - **IF** any blocking record exists - `inst-mb-if-blocked`
   1. [x] - `p1` - **RETURN** `RECOVERY_REQUIRED` naming every blocking record; no record is deleted automatically - `inst-mb-return-blocked`
5. [x] - `p1` - **IF** the engine reads an entry carrying `pendingPostCommit` for a new upgrade or restore - `inst-mb-if-pending-post-commit`
   1. [x] - `p1` - **RETURN** `RECOVERY_REQUIRED` naming the name and its record, before any plan or no-op is computed - `inst-mb-return-pending-post-commit`
6. [x] - `p1` - On approval of an upgrade or restore plan, before any effect, record the transition's immutable intent (name, `from`/`to`, pre-transition entry, plan digest, candidate hash, the payload footprint with each path's pre-commit content hash, initial inventory/AI task status): write the project receipt as `preparing`, then the reservation under the inventory root, then advance the receipt to `prepared`; the commit-point state write carries the transition's `pendingPostCommit` record - `inst-mb-begin-transition`
7. [x] - `p1` - **IF** the engine returns success - `inst-mb-if-verified-commit`
   1. [x] - `p1` - **IF** the entry records this transition's post-commit work with no task pending, release the transition as `committed`, clearing the entry's `pendingPostCommit`; **ELSE** fail as an internal error that names `--recover`, the records kept - `inst-mb-release-committed`
8. [x] - `p1` - **ELSE IF** the entry is still the pre-transition entry and every footprint path is at its pre-commit content - `inst-mb-if-no-effect`

9. [x] - `p1` - **ELSE** - `inst-mb-else-guarded`
   1. [x] - `p1` - **RETURN** `RECOVERY_REQUIRED` with the engine's own failure as its cause, whether the transition committed, its receipt, and (when not committed) every changed footprint path; the records stay for `--recover` - `inst-mb-return-guarded`
10. [x] - `p1` - A release verifies the reservation against the immutable record, persists `finalizing` with the verified terminal entry, runs the entry's record clearing, then removes the reservation and last the receipt; a reservation that is missing for a `prepared` transition or disagrees with its receipt is refused with `RECOVERY_REQUIRED` and nothing is removed - `inst-mb-finalize`
11. [x] - `p1` - Release the mutex whatever the command's outcome - `inst-mb-release-mutex`

## 4. States (CDSL)

### Upgrade Lifecycle

- [x] `p2` - **ID**: `cpt-frontx-state-upgrade-changeset-lifecycle`

This machine models exactly one engine invocation, forward or restore, from the moment it reads its baseline to the moment it terminates. A later invocation — another `upgrade`, or `--restore` — is a fresh instance of this same machine, starting again at `BASELINE_READ`; no state below is given an outgoing transition back to it.

**States**: BASELINE_READ, VALIDATED, REFUSED, NOOP, PRESENTED, APPROVED, COMMITTED, DECLINED

**Initial State**: BASELINE_READ

**Transitions**:
1. [x] - `p1` - **FROM** BASELINE_READ **TO** VALIDATED **WHEN** the new origin resolves, declares the same identity as the registered name, and validates against every target in `targets[]` - `inst-st-read-to-validated`
2. [x] - `p1` - **FROM** BASELINE_READ **TO** REFUSED **WHEN** the name is not registered, its `targets[]` is empty, no preceding `{origin, version}` is recorded for a restore (`NOTHING_TO_RESTORE`), the recorded `version` no longer matches what the recorded `origin` reports (`VERSION_MISMATCH`), the new origin cannot be resolved, it declares a different identity, a file inside any target has both moved away from the baseline and does not already match the candidate (`CONTENT_CONFLICT`), or another registered target nests inside ground the candidate newly claims (`TARGET_CONFLICT`); `templates[name]` is unchanged for every target - `inst-st-read-to-refused`
3. [x] - `p1` - **FROM** BASELINE_READ **TO** NOOP **WHEN** the resolved candidate's `{origin, version}` equals the baseline's own; no plan is computed, no destination is written (the document itself may still acquire a missing `excludedSubtrees`, per `inst-record-noop-exclusions`), and, for a restore, the preceding pair is left exactly as it is - `inst-st-read-to-noop`
4. [x] - `p1` - **FROM** VALIDATED **TO** PRESENTED **WHEN** the transition has been built and shown to the developer for review - `inst-st-validated-to-presented`
5. [x] - `p1` - **FROM** PRESENTED **TO** APPROVED **WHEN** the developer grants explicit approval - `inst-st-presented-to-approved`
6. [x] - `p1` - **FROM** PRESENTED **TO** DECLINED **WHEN** the developer declines the transition; nothing is written - `inst-st-presented-to-declined`
7. [x] - `p1` - **FROM** APPROVED **TO** REFUSED **WHEN** the pre-rename verification finds a destination has drifted from what classification saw (`CONTENT_CONFLICT`, no destination touched), or an I/O failure during the destination-write step is caught and recovery succeeds (`INTERNAL`, every target and `templates[name]` exactly as before) or itself fails (`INTERNAL` naming both failures, `templates[name]` untouched though a destination may not be at baseline); nothing is committed to the project state store in any of these - `inst-st-approved-to-refused`
8. [x] - `p1` - **FROM** APPROVED **TO** COMMITTED **WHEN** the engine applies the transition within every target's effective ownership and commits `origin`/`version` in a single state-document write for the name, including when the inventory promotion after that commit point fails (`INTERNAL` naming the slot, the transition itself still landing here) — a restore's own commit lands in this same state, not a distinct one, since restore is this engine run against the recorded preceding `{origin, version}` as its candidate - `inst-st-approved-to-committed`

## 5. Definitions of Done

### All-Targets Validation and Review

- [x] `p1` - **ID**: `cpt-frontx-dod-upgrade-changeset-computation`

The system **MUST** read a registered name's `{origin, version, targets[]}` entry from the project state store (`cpt-frontx-feature-composed-provenance`) as the sole baseline, refusing with `TEMPLATE_NOT_REGISTERED` when the name has no entry, with `TARGET_NOT_APPLIED` when its `targets[]` is empty, and with `VERSION_MISMATCH` when the recorded `version` no longer matches what the recorded `origin` reports — a baseline the project state misreports is not a baseline to diff from; resolve a candidate new origin through the shared resolver without replacing the registered name's own entry in the local template inventory, confirm it declares the same manifest identity as the registered name, treat a candidate resolving to the baseline's own `{origin, version}` as an idempotent no-op that computes no plan and consumes no reversal, and otherwise compute, once per target, the effective ownership boundary from the candidate manifest's declared `excludedSubtrees` alone — never the baseline manifest's, and never recomputed per path. Every payload path that falls outside that boundary, for any of its subtraction terms — the candidate manifest's `excludedSubtrees` now excluding ground the baseline owned, or `projectOwnedRoots`, `.frontx`, a reserved environment entry, or the template's own local origin folder excluding it regardless of what changed between the two manifests, including ground a nested other template's target already legitimately occupies — **MUST** be left untouched on disk and reported `SKIPPED`; a payload path inside that boundary which instead collides with the reserved temporary-file naming convention **MUST** likewise be excluded from classification and reported `SKIPPED`, naming that collision, never silently dropped from the plan; ground the candidate no longer excludes **MUST** be classified as ordinary eligible ground, refusing with `TARGET_CONFLICT` where another registered target nests inside it, including a sibling target under the same name. For every path inside the resulting boundary, the system **MUST** test first, before any other classification, whether the on-disk content already equals the candidate's — including when both are absent — and only then apply `ADD`/`REPLACE`/`REMOVE`/`KEEP_LOCAL`/`UNCHANGED`; comparison is defined over absence explicitly (an absent path is unequal to any content, two absences are equal), and a payload path where the disk holds a directory, a symlink, or a special file (a FIFO, socket, or device — anything that is neither a regular file, a directory, nor a symlink) instead of a regular file, or where any directory component from the project root down to the leaf's parent — `target`'s own component included, never only the components strictly below it — is itself a symlink, an ordinary regular file, or a special file, **MUST** refuse fail-closed as a doubly-changed path, since none of those shapes can be compared against a payload's declared content without risking a read or a write landing somewhere the plan never named, and a special file's own content **MUST NOT** be read to reach that conclusion, since opening one for reading can block forever; `target`'s own component is included because it is a string recorded in the project state store, never canonicalized by this engine before classification the way `apply`'s pre-flight canonicalizes a batch's own target. An ancestor that is a special file **MUST** be refused exactly like a symlinked or a plain-file ancestor, never treated as the permitted directory shape it superficially resembles to a caller that does not distinguish the two: every path beneath it is otherwise unreadable (the underlying `lstat` fails), and reporting that failure as an ordinary absence would satisfy the disk-equals-candidate precedence rule above for content this engine never actually managed to read — a false success, not merely a misdirected comparison. The system **MUST** judge ownership and containment on the NORMALISED project-relative spelling of every location it is about to compare, read or write — the recorded `target` and every payload path re-rooted under it — and **MUST NOT** enumerate, compare, read from disk, probe, or plan a location that is not already spelled as the one location it names (absolute, climbing out of the project root, or carrying a `.`, `..` or empty segment or a trailing separator): the whole upgrade is refused with `INVALID_PATH` instead, whether or not the resolver's bundle-key check upstream would have caught it; and the real disk adapter that serves the classification's reads **MUST** refuse, without calling `lstat` or reading, any absolute path outside the project root. The system **MUST** present the resulting operation plan, including every `SKIPPED` path, to the developer before writing any project file, and **MUST** refuse the entire upgrade — writing nothing and leaving every target's recorded `origin`/`version` and the inventory entry unchanged — with `ORIGIN_UNAVAILABLE` when the origin cannot be resolved, with `REGISTRATION_CONFLICT` when it declares a different identity, with `INVALID_PATH` naming every location not spelled as the one it names, ahead of every other refusal, and with `INVALID_PATH` naming every target and path where the leaf itself, or an ancestor, is a symlink whose resolved target escapes the project root (checked, and refused, ahead of the content check below, since whether a path is addressable inside the project at all is the more fundamental question), with `CONTENT_CONFLICT` naming every remaining target and path where a file has both moved away from the baseline and does not already match the candidate — separately naming, within that report, which of those paths are instead uncomparable because the disk shape cannot be compared at all rather than because content genuinely drifted — or with `TARGET_CONFLICT` naming every target and template where the candidate newly claims nested ground (`target`).

### All-Targets Commit

- [x] `p1` - **ID**: `cpt-frontx-dod-upgrade-changeset-apply`

The system **MUST** land an approved operation plan through a staged write: reclaim any stale REGULAR FILE matching the reserved naming convention below already inside any target's effective ownership — the only shape this algorithm's own convention ever produces at such a path, and so the only shape it can reclaim with any confidence that it is reclaiming its own past litter — then, for every `ADD`/`REPLACE` operation, before materialising anything, verify that its own reserved temporary path holds nothing but a regular file or an absence, refusing the whole upgrade with `CONTENT_CONFLICT` naming every destination whose temporary path instead holds a directory, a symlink, or a special file (a FIFO, socket, or device) — with nothing yet materialised or touched anywhere — since this algorithm never produces any of those shapes there itself, so finding one there is proof that something else did, and writing through it (following a live symlink to wherever it actually points) or opening it (blocking forever on a FIFO with no writer) is exactly the outcome this refusal exists to make impossible; only once that verification passes **MUST** the system materialise every `ADD`/`REPLACE` operation's new content into a temporary file beside its destination, named by appending a reserved suffix this engine alone uses to the destination's own filename, mutating no destination path in this step; classification **MUST** exclude every path matching that convention from every comparison, so a crash cannot leave litter that later classifies as a developer's own file. Once every temporary file for every target of the name exists, and immediately before the first rename, the system **MUST** verify that every destination the plan touches still holds exactly the content classification saw for it, refusing the whole upgrade with `CONTENT_CONFLICT` naming every drifted destination — with no destination touched — when it does not; this is a precondition check, never a recomputation. Only then **MUST** the system land each `ADD`/`REPLACE` by an atomic rename over its destination — creating any parent directory the rename needs — and unlink each `REMOVE` without removing the directory it leaves empty, never opening a `KEEP_LOCAL` or `UNCHANGED` path for writing, confined throughout to each target's effective ownership and never to a nested target belonging to another registered target, including a sibling target under the same name. As the single atomic write that is this transition's commit point, after every target's destination writes have landed, the system **MUST** commit `origin` and `version` to the approved plan's `to` values together with the name's immediately preceding `{origin, version}` — a write to the project state store alone, never described together with the step after it as one atomic write. As a separate step after that commit point, the system **MUST** promote the committed origin into the registered name's own entry in the local template inventory (for an installed remote origin, by re-resolving it through the bounded update, which runs even when its ref and content match the existing slot; a local `path:` origin or a name never installed has no slot to promote into), and, if that promotion fails, **MUST** return `INTERNAL` naming the slot it could not replace while leaving the transition itself committed, because the slot's content is re-derivable by resolving the recorded origin. On any I/O failure caught inside the staged write — whether while reclaiming a stale temporary file, verifying temp occupancy, materialising a new one, verifying a destination, or landing a rename or unlink — the system **MUST** attempt to return every destination path already landed at the point of failure to its baseline state — writing baseline content where the baseline carries the path, unlinking where it does not, since a landed `ADD` is reversed by unlinking rather than by writing content the baseline does not have — **MUST** also remove every temporary file this attempt materialised whose operation never reached the rename phase, since it was never a destination and has no baseline content to restore, only its own existence to undo, and **MUST** write nothing to the project state store or the inventory entry either way; a failure caught before the first rename has landed no destination, so this recovery is vacuously, trivially successful. A temporary file that cannot be removed is exactly as much a recovery failure as a destination that cannot be returned to baseline — the two are named together, never distinguished into a separate report, so a failure to sweep this attempt's own litter can never be reported as full recovery. When that recovery succeeds — every destination back at baseline AND every such temporary file removed — every target is left exactly as it was before the attempt and the system **RETURN**s `INTERNAL` naming the original failure; when recovery itself fails for one or more paths or temporary files, the system **RETURN**s `INTERNAL` naming both the original failure and every path or temporary file recovery could not return or remove. A hard crash that this catch never observes runs no recovery at all; before the commit point, the recorded entry still names the baseline, and re-running the identical upgrade **MUST** converge on the intended state through the disk-equals-candidate precedence rule rather than refusing, under the stated preconditions (the same baseline and candidate still resolve, and nothing else — no concurrent process, no outside edit of the project, the registered origin or the state document — intervened; there is no cross-process lock), writing the same project state document, protection fields included, an uninterrupted run would have written, and reclaiming any stale reserved-suffix temporary regular file the crash left behind inside a target's effective ownership (the project state store's own `.project.json.<uuid>.tmp` is not reclaimed) — no rollback journal is retained, since the baseline payload recovery depends on is re-resolvable rather than stored. A successful commit **MUST** refresh the name's CLI-owned AI-extension bundle at `.frontx/ai/<manifest-name>/` from the new payload, through the same CLI-owned step `apply` and `delete` use (`cpt-frontx-algo-cli-scaffolding-ai-bundle`), never through the template's own ownership, and, if that refresh fails, **MUST** return `INTERNAL` naming the bundle it could not refresh while leaving the transition and the promoted inventory entry standing, defined the same way a promotion failure is (`target`). The single project-state write that IS this transition's commit point **MUST** land LAST, after every destination write, and its own failure — whether the document it must re-read is malformed or the write itself fails — **MUST** be reported as a typed `INTERNAL` outcome rather than escaping this engine's declared return shape as a thrown error: a store write escaping its function's `{ok:false}` contract after project files have already been rewritten is exactly the defect the retired region-merge engine carried for its separate provenance document. That outcome **MUST NOT** roll the landed destinations back: the recorded entry still names the baseline, so re-running the identical upgrade **MUST** converge (`inst-cls-if-unchanged`'s disk-equals-candidate precedence) rather than refuse, under the stated preconditions (the same baseline and candidate still resolve, and nothing else — no concurrent process, no outside edit of the project, the registered origin or the state document — intervened; there is no cross-process lock), with the same protection fields an uninterrupted run would have recorded — and undoing approved work to recover a document that was never written would be the strictly worse answer (`target`).

Restoring the snapshot can itself fail. The system **MUST** then still attempt every other snapshotted file, and **MUST** return a typed failure that keeps the application error as its primary message and names each file it could not restore. It **MUST NOT** report the project as restored.

## 6. Acceptance Criteria

- [x] Invoking `upgrade <templateName> <new-origin>` for a registered name with at least one applied target produces a reviewable operation plan covering every target under that name, and writes no project file until the developer approves.
- [x] The baseline read for the upgrade is exactly `templates[templateName].{origin, version}` from the single project state document — no per-instance provenance record or per-file hash set is read or required to exist.
- [x] Approving the operation plan commits `templates[templateName].origin`/`.version` and its immediately preceding `{origin, version}` in a single state-document write, lands every `ADD`/`REPLACE`/`REMOVE` operation within every target's effective ownership, and replaces the local inventory entry; declining leaves the repository, the project state store, and the inventory entry byte-for-byte unchanged.
- [x] A file inside a target's effective ownership that only the developer has changed since the baseline survives an upgrade untouched, classified `KEEP_LOCAL`.
- [x] A file inside a target's effective ownership changed by both the candidate and the developer since the baseline, and not already matching the candidate, refuses the whole upgrade with `CONTENT_CONFLICT`, naming every such target and path, and writes nothing to any target, to the project state store, or to the local inventory entry.
- [x] A payload path where the disk holds a directory, a symlink, or a special file (a FIFO, socket, or device — anything that is neither a regular file, a directory, nor a symlink) instead of a regular file refuses fail-closed with `CONTENT_CONFLICT`, with no comparison attempted for that path and, for a special file, its content never read to reach that refusal; the identical refusal applies when any directory component from the project root down to the leaf's parent — the target's own path component included, not only the components strictly below it — is a symlink that resolves inside the project, an ordinary regular file, or a special file, because such a component makes the OS resolve the path elsewhere than where the plan names it (a symlink), makes the leaf unreachable at all (a file where a directory is required), or makes every path beneath it read back as an unreadable absence rather than as content the engine could actually inspect (a special file), on both the classification read and, absent this refusal, the eventual write. A special-file ancestor's own absence-shaped failure is never allowed to satisfy the disk-equals-candidate precedence rule for a path beneath it — the fail-closed refusal here is exactly what stops that false success from ever being reported. When that symlink — the leaf itself, or an ancestor — instead resolves to a target that escapes the project root, the refusal is `INVALID_PATH`, not `CONTENT_CONFLICT` — the same code `apply`'s own pre-flight containment check reports for the identical on-disk shape — naming a more fundamental problem than an internal symlink does.
- [x] `INVALID_PATH` for an escaping symlink — at the leaf itself, or at an ancestor — is refused before `CONTENT_CONFLICT` is ever computed for the same target, and names every offending target and path in one report, having classified every target first.
- [x] A payload path that climbs and comes back (`app/../other/x.txt` under target `app`, `src/../.frontx/injected.json` under the project root), an absolute payload path, a payload path with a `.` or empty segment, and a recorded `target` spelled the same way (`app/../.frontx`, `../outside`, `app/`) are each refused with `INVALID_PATH` naming the location and why, having been neither read from disk nor probed through their ancestors nor planned, with nothing written anywhere and the plan never presented — judged on the normalised project-relative spelling, so that a path an ownership comparison would place inside a target while it lands outside it, or outside the CLI's own `.frontx` exclusion, never reaches a write; this holds with the resolver's bundle-key check removed. The real disk read adapter refuses, without calling `lstat`, any path outside the project root, so even a location this algorithm did not judge cannot be reported on.
- [x] A `CONTENT_CONFLICT` refusal separately names, within the doubly-changed paths it reports, which are uncomparable because of an unreadable disk shape (a directory, a symlink, or a special file at the leaf, or a symlink, a regular file, or a special file at an ancestor) rather than because content genuinely drifted from the baseline, and names the specific component responsible for each — the two causes carry different remedies, so a developer is never sent looking for a content difference that does not exist, or left to find the offending component by hand.
- [x] The boundary a plan writes through is computed once per target, from the candidate manifest's declared `excludedSubtrees` alone, never from the baseline manifest's and never recomputed per path; every payload path that falls outside that boundary for any of its subtraction terms — `excludedSubtrees`, `projectOwnedRoots`, `.frontx`, a reserved environment entry, the template's own local origin folder, or ground another registered target, including a sibling target under the same name, already legitimately occupies — is left untouched on disk and reported `SKIPPED`, never removed and never written, not only the ground the candidate newly excludes that the baseline owned.

- [x] A file the developer created with content byte-identical to what the candidate adds, a file the candidate removes that the developer already deleted, and every path a crashed run had already written before dying, all classify with nothing left to do and refuse nothing — the on-disk-equals-candidate precedence rule is tested before every other branch, including when both are absent.
- [x] A file both the baseline and the candidate carry identically that the developer has deleted classifies `KEEP_LOCAL`, the deletion standing as the edit; a file the developer deleted that the candidate also changes refuses with `CONTENT_CONFLICT`.
- [x] A declined operation plan writes nothing to any target, to the project state store, or to the local inventory entry.
- [x] `upgrade` against a name with no registered entry returns `TEMPLATE_NOT_REGISTERED`; against a name whose `targets` array is empty, the engine refuses with `TARGET_NOT_APPLIED` and directs the developer to `register --replace`.
- [x] A registered name whose recorded `version` no longer matches what its recorded `origin` reports is refused with `VERSION_MISMATCH` before the candidate origin is resolved and before any target is classified, naming the recorded and the reported version.
- [x] A new origin that fails to resolve returns `ORIGIN_UNAVAILABLE` before any target is classified.
- [x] A new origin whose manifest declares an identity different from the registered name being upgraded is refused with `REGISTRATION_CONFLICT`, naming both identities, with no target classified and no operation plan computed.
- [x] A new origin that resolves to the name's already-recorded `{origin, version}` is an idempotent no-op: no operation plan is computed, no destination is written, and the name's preceding pair is left unchanged.

Recovery never reports a full recovery while a temporary file it materialised remains on disk: a failure to remove one is folded into the same "could not return" report a destination that cannot be restored gets, never omitted from it.

- [x] Before materialising anything, a destination whose own reserved temporary path already holds a directory, a symlink (whether it resolves inside or outside the project, dangling or live), or a special file (a FIFO, socket, or device) refuses the whole upgrade with `CONTENT_CONFLICT` naming every such destination, with nothing materialised or touched anywhere — this algorithm never produces any of those shapes at a reserved-suffix path itself, so it is never reclaimed, never opened, and never written or renamed through; only a regular file or an absence at that path lets materialisation proceed.
